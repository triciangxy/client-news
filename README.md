# Client Pulse

Two internal tools for the APAC private banking desk:

- **`index.html`** — dashboard tracking news and price moves across key clients.
- **`wealth.html`** — Source of Wealth estimator: sizes a prospect's net worth from their listed company's annual report before you walk into the meeting.

## What's in this repo

| File | What it does |
|---|---|
| `index.html` | The dashboard. Reads `data.json` and renders. |
| `wealth.html` | Source of Wealth estimator. Standalone — no data feed, no build step. |
| `data.json` | Cached headlines + quotes. Regenerated by the workflow. |
| `fetch_news.py` | Python script that pulls news + quotes. Runs on GitHub Actions. |
| `.github/workflows/refresh.yml` | Scheduled job that runs `fetch_news.py` and commits the result. |

## How it works

1. Every 30 minutes (during APAC business hours, Mon–Fri), GitHub Actions runs `fetch_news.py` on a free Ubuntu runner.
2. The script fetches stock quotes (Yahoo Finance chart endpoint) and headlines (Google News RSS filtered to each client's domain).
3. It writes results to `data.json` and commits it back to the repo.
4. GitHub Pages serves `index.html`, which reads the latest `data.json` and renders the cards.

No CORS proxies. No paid APIs. No server infrastructure to maintain.

## First-time deployment (one-time setup, ~10 min)

### Step 1 — Create the repo

1. On GitHub, click **New repository**.
2. Name it something unguessable, e.g. `cp-internal-x7k2`. **Public** (Pages on private repos requires a paid plan).
3. Don't add a README or .gitignore — we'll push the files directly.

### Step 2 — Push these files

Drag and drop the files into the repo on github.com (use **Add file → Upload files**):
- `index.html`
- `wealth.html`
- `data.json` (the starter file with the most recent run included)
- `fetch_news.py`
- `.github/workflows/refresh.yml` (you'll need to type the path manually since GitHub's drag-and-drop doesn't preserve folders — easier: create the file via **Add file → Create new file**, name it `.github/workflows/refresh.yml`, paste the contents)

Commit to the `main` branch.

### Step 3 — Enable GitHub Pages

1. Repo → **Settings** → **Pages** (left sidebar).
2. **Source**: Deploy from a branch.
3. **Branch**: `main`, folder `/ (root)`. Save.
4. After ~30 seconds, the URL appears at the top of the Pages settings: `https://<your-username>.github.io/cp-internal-x7k2/`.

### Step 4 — Grant the workflow permission to push

1. Repo → **Settings** → **Actions** → **General** (left sidebar).
2. Scroll to **Workflow permissions**.
3. Select **Read and write permissions**. Save.

This lets the scheduled job commit updates to `data.json`.

### Step 5 — Trigger the first run manually

1. Repo → **Actions** tab.
2. Click **Refresh Client Pulse Data** on the left.
3. Click **Run workflow** → **Run workflow**.
4. Wait ~30 seconds. It should commit a fresh `data.json`.

Open your Pages URL — you should see the dashboard with live data.

## The Source of Wealth estimator (`wealth.html`)

Open `<your-pages-url>/wealth.html`. It is a single static page — no data feed, no
workflow, nothing to deploy beyond the file itself. Two examples ship with it, so you
can see a completed case before entering your own:

- **Listed example** — the case this tool is built for: a chairman and a co-founder of
  an illustrative listed manufacturer, accounts audited from the 2011 IPO onward, both
  stakes marked to market. Loads by default. The company and the people are invented.
- **Memo example** — the desk's original reference case (the family manufacturer with a
  2019 transfer between spouses), anonymised, for checking the methodology against the
  written memo.

**Scope:** directors and controlling shareholders of *listed* companies, where an
audited annual report gives you a defensible net profit and equity figure to work from.

### The methodology

The estimator implements the desk's accumulated-income approach as an ordered
waterfall. Every step is visible on screen, in the step table, and in the draft memo
language, so any number in the file can be traced back to an input:

| Step | What it does | Default |
|---|---|---|
| Distributable profit | Net profit less what the business retains | 40% retained |
| Gross accumulation | Distributable × credited years × ownership %, per ownership period | — |
| Inflation haircut | Erosion of the real value of historic earnings | 20% |
| Prudence discount | Applied **only to periods without audited statements** | 60% |
| Current holding | Their share of book equity — or market cap for a disclosed listed stake | book equity |
| Tax & personal expenses | Final haircut on everything accumulated | 20% |
| Other observed assets | Added after the discounts, not subject to them | — |

**Year recognition** is the judgement call that moves the answer most. The default
credits 48% of each ownership span — roughly the memo convention of discounting 24 of
46 years. Spans are counted inclusively (1972–2018 is 47 years), and the auto figure
is a suggestion: type over the credited-years box on any period to fix it manually.

**Ownership periods** handle transfers. A founder holding 50% until 2018 and a spouse
holding 100% from 2019 are two cards, the second with two periods.

**The prudence discount is per period, not per person** — tick **Aud** on each period
covered by audited statements. This matters for the listed names this tool is for: a
director who took the company public in 2011 has audited accounts from 2011 onward and
unaudited ones before it, and only the pre-IPO years should carry the 60% haircut.
Discounting the audited years too understates the prospect badly, which is the most
common way this methodology goes wrong on a listed name.

**The sensitivity band** under the headline is not a multiplier on the answer — it is
the whole model re-run with the recognition ratio and prudence discount flexed, so the
conservative and upper cases are as defensible as the base case.

**Cross-check lenses** value the same person three other ways — book equity share,
market value of their stake, and cumulative dividends received. They are independent of
the accumulated-income path. When they diverge sharply from the primary estimate, that
is the thing to resolve before the meeting, not after.

### Working a case

1. Enter the company's reporting currency and **overwrite the FX rate with your desk
   rate** — the built-in rates are indicative starting points only.
2. Set "figures entered in" to match how you're typing numbers (units / thousands /
   millions), then enter net profit and total equity straight off the annual report.
3. Use a through-cycle average net profit, not a peak year. The profit history table
   computes one for you.
4. Add a principal per individual, with an ownership period per holding change, and
   tick **Aud** on the periods covered by audited statements.
5. For a current listed stake, set "value their current holding at" to **market cap** —
   book equity understates a disclosed holding in a listed name, often heavily.
6. Read the waterfall, then **Copy text** to lift the draft memo language into the
   source-of-wealth section of the call report.

### Saving and sharing

Cases save to your browser's local storage (**Save** / **Saved ▾**) and export as JSON
for handover. **Print / PDF** produces a clean one-piece memo with the input panel
stripped out.

Nothing is uploaded anywhere. There is no server, no analytics, and no network call
beyond the web font — prospect names and figures stay in your browser.

### Limits worth stating in the file

The output is an *indicative pre-meeting size*, built from public filings plus stated
assumptions. It is not a substitute for documented source-of-wealth verification under
KYC/AML policy, and it does not attempt to capture inherited wealth, non-operating
assets, borrowings against the stake, or holdings outside the subject company. Check
every figure against the filing before it leaves your hands.

## Editing the client list

Edit the `CLIENTS` list at the top of `fetch_news.py`. Each entry can have:

| Field | Required | Notes |
|---|---|---|
| `name` | yes | Display name shown on the card |
| `short` | yes | Short key used internally |
| `type` | yes | One of: `listed`, `sovereign`, `pension`, `insurance`, `bank` |
| `country` | yes | Display label |
| `ticker` | listed only | Yahoo Finance ticker (e.g. `1299.HK`, `7182.T`, `055550.KS`) |
| `aum` | private only | AUM in USD billions, for display |
| `earnings` | optional | ISO date `YYYY-MM-DD` of next confirmed earnings |
| `blurb` | optional | One-line description shown in the detail drawer |
| `newsroom` | optional | URL to the client's press page |
| `sources` | yes | List of news sources, tried in priority order |

Each source has `type` (badge category), `label` (what shows on the card), `kind` (`google-news` or `rss`), and either `query` (for google-news) or `url` (for rss).

After editing, commit the change. The next scheduled run will pick it up, or trigger it manually from the Actions tab.

## Schedule

The default cron `*/30 0-10 * * 1-5` runs every 30 min from 00:00–10:00 UTC, Monday–Friday (Singapore: 08:00–18:00 SGT). Edit `.github/workflows/refresh.yml` to change it.

GitHub Actions sometimes delays scheduled jobs by a few minutes when their runners are busy — that's normal, not a bug.

## Troubleshooting

**"Could not load data.json" error on the page**
→ The workflow hasn't run yet, or it failed. Check the Actions tab.

**Workflow fails with permission error**
→ You skipped Step 4 above. Go back and grant write permissions.

**Cards show "no source"**
→ The fetcher couldn't reach Google News for that client. Could be transient — try re-running. If persistent, the `site:` filter for that domain may need to be broadened.

**Yahoo quote endpoint stops working**
→ Yahoo occasionally changes endpoints. If quotes go missing, the chart endpoint in `fetch_quote_chart()` is the most-stable replacement; for production-grade reliability, swap to a paid feed (Polygon, IEX Cloud, FMP).

## Not for client distribution

Both tools are for internal use. The dashboard aggregates publicly-available news and
price data; not investment advice. The wealth estimator produces indicative internal
sizing from public filings; it is not a valuation, not advice, and not a client-facing
document.
