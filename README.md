# Client Pulse

Three internal tools for the APAC private banking desk:

- **`index.html`** — dashboard tracking news and price moves across key clients.
- **`prospects.html`** — prospect screener: sizes every director on a listed board from public exchange filings. Start here.
- **`wealth.html`** — full Source of Wealth estimator: the detailed, line-by-line build-up you need once a prospect becomes a client.

**Which one do I want?** The screener answers *"is this person worth a meeting?"* in
two numbers, straight off the exchange. The estimator answers *"how did they get their
money, and can I evidence it?"* in seven, and takes real work to fill in. Screen first,
build the file later.

## What's in this repo

| File | What it does |
|---|---|
| `index.html` | The dashboard. Reads `data.json` and renders. |
| `prospects.html` | Prospect screener. Reads `twse.json`, falls back to sample data. |
| `wealth.html` | Full Source of Wealth estimator. Standalone — no data feed. |
| `data.json` | Cached headlines + quotes. Regenerated by the workflow. |
| `twse.json` | Cached TWSE director holdings + remuneration. Regenerated by the workflow. |
| `fetch_news.py` | Pulls news + quotes. Runs on GitHub Actions. |
| `fetch_twse.py` | Pulls TWSE director disclosures. Runs on GitHub Actions. |
| `.github/workflows/refresh.yml` | Scheduled job for `fetch_news.py`. |
| `.github/workflows/twse.yml` | Scheduled job for `fetch_twse.py`. |

## How it works

1. Every 30 minutes (during APAC business hours, Mon–Fri), GitHub Actions runs `fetch_news.py` on a free Ubuntu runner.
2. The script fetches stock quotes (Yahoo Finance chart endpoint) and headlines (Google News RSS filtered to each client's domain).
3. It writes results to `data.json` and commits it back to the repo.
4. GitHub Pages serves `index.html`, which reads the latest `data.json` and renders the cards.

No CORS proxies. No paid APIs. No server infrastructure to maintain.

## First-time deployment (one-time setup, ~10 min)

### Step 1 — Create the repo

1. On GitHub, click **New repository**.
2. Name it something unguessable, e.g. `cp-internal-x7k2`. **Public** (Pages on private repos requires a paid plan).
3. Don't add a README or .gitignore — we'll push the files directly.

### Step 2 — Push these files

Drag and drop the files into the repo on github.com (use **Add file → Upload files**):
- `index.html`
- `wealth.html`
- `data.json` (the starter file with the most recent run included)
- `fetch_news.py`
- `.github/workflows/refresh.yml` (you'll need to type the path manually since GitHub's drag-and-drop doesn't preserve folders — easier: create the file via **Add file → Create new file**, name it `.github/workflows/refresh.yml`, paste the contents)

Commit to the `main` branch.

### Step 3 — Enable GitHub Pages

1. Repo → **Settings** → **Pages** (left sidebar).
2. **Source**: Deploy from a branch.
3. **Branch**: `main`, folder `/ (root)`. Save.
4. After ~30 seconds, the URL appears at the top of the Pages settings: `https://<your-username>.github.io/cp-internal-x7k2/`.

### Step 4 — Grant the workflow permission to push

1. Repo → **Settings** → **Actions** → **General** (left sidebar).
2. Scroll to **Workflow permissions**.
3. Select **Read and write permissions**. Save.

This lets the scheduled job commit updates to `data.json`.

### Step 5 — Trigger the first run manually

1. Repo → **Actions** tab.
2. Click **Refresh Client Pulse Data** on the left.
3. Click **Run workflow** → **Run workflow**.
4. Wait ~30 seconds. It should commit a fresh `data.json`.

Open your Pages URL — you should see the dashboard with live data.

## The prospect screener (`prospects.html`)

Search any listed company by code, English name or Chinese name, click in, and get
every director on that board sized in one table. Two components, both from public
exchange disclosure:

```
estimated net worth  =  shares held × share price × (1 − stake discount)
                     +  annual remuneration × years on board × savings rate
```

That's the whole model. The stake discount (default 20%) exists because a board-sized
position can't be sold at the screen price. The savings rate (default 40%) turns pay
earned into wealth retained. Sort by any column, and **Copy table** lifts the whole
board into a note.

**Years on board is read from the filing — there is no tenure assumption.** TWSE
discloses 初次選任日期 (date first elected) for each director, so a founder on the board
since 1986 accumulates over 40 years while an independent director appointed in 2020
accumulates over six. First-elected is used in preference to 選任日期, which resets on
re-election and would make a thirty-year founder look like a three-year appointee.

Where no date is disclosed the pay component is **dropped rather than guessed**: that row
reports stake value only, is flagged `!`, and the note says how many rows are affected.
It is understated by whatever their board pay has accumulated to, which is the safe
direction — but check those rows by hand before you act on them.

**Every figure links back to its source.** Under the company name are click-throughs to
the MOPS/TWSE pages behind the numbers — company profile, director holdings, director
remuneration, price history — so any figure can be checked against the exchange in one
click. The URL templates live in a single `SOURCE_LINKS` constant at the top of the
script block in `prospects.html`; if the exchange moves a page, fix it there.

The **quick estimate** panel at the bottom runs the same two lines on figures you type
in, for a prospect whose company isn't in the feed.

Arrow keys and Enter work in the search box, and opening a company sets the URL hash
(`prospects.html#2317`), so you can bookmark a board or paste it to a colleague.

### Two ways to deploy

| | GitHub Pages | Cloudflare Worker |
|---|---|---|
| Public URL | `<user>.github.io/client-news/prospects.html` | `pb-sow.<subdomain>.workers.dev` |
| Data freshness | Last scheduled Action run | Live, on request |
| Needs | Nothing beyond this repo | A free Cloudflare account |
| How TWSE is reached | GitHub Action fetches and commits JSON | Worker fetches server-side per request |

Both are public URLs anyone can open — no account, no login, nothing to install.

**Why the difference matters.** A browser can't call TWSE: their endpoints send no
CORS headers, so the request is blocked before it leaves the page. Static hosting has
no server to get around that, which is why the Pages build routes the fetch through a
scheduled GitHub Action that commits JSON into the repo.

A Cloudflare Worker *is* a server. It calls TWSE directly, per request, and hands the
result back as same-origin JSON — no scheduled job, no committed data, always current.
That is the whole trick behind any "it pulls live from the regulator's site" demo you'll
see on a `*.workers.dev` URL.

The page tries both and degrades cleanly: `/api/twse/index` (live Worker) → `twse.json`
(committed snapshot) → built-in sample data. The header says which tier answered.

#### Deploying the Worker

```bash
npm install -g wrangler
wrangler login          # opens a browser, free account is enough
wrangler deploy         # prints your public URL
```

`wrangler.toml` serves the repo's static files and routes `/api/*` to `worker.js`.
Endpoints:

| Route | Returns |
|---|---|
| `/api/twse/health` | Which TWSE dataset answered for each role, and row counts |
| `/api/twse/index` | Light index of every listed company |
| `/api/twse/company/<code>` | One board: holdings, pay, election dates |

**Open `/api/twse/health` first.** It is the selftest, in a browser, against live TWSE —
it tells you whether the dataset IDs still resolve and how many rows each returned.

### Connecting it to TWSE via GitHub Actions

The browser can't call TWSE directly (no CORS headers on their endpoints, and this is a
static site with no server). So the fetch runs on GitHub Actions and commits the result
back to the repo, exactly like the news dashboard already does. **No API key or account
is needed** — TWSE open data is public and unauthenticated.

1. Make sure Actions can push: **Settings → Actions → General → Workflow permissions →
   Read and write permissions**. This is the same setting the news job needs, so if the
   dashboard is already refreshing, you're done.
2. Go to **Actions → Refresh TWSE Director Data → Run workflow**, tick **selftest**, and
   run it. This writes nothing — it just prints which TWSE dataset answered for each
   role. Check the log shows real row counts rather than zeros.
3. Run it again with **selftest** unticked. It fetches the whole market and commits
   `twse.json` plus the `twse/` shards.
4. Open `prospects.html`. The amber sample-data banner disappears once a real index is
   committed.

After that it refreshes itself weekdays at 06:00 UTC (14:00 Taipei, after the 13:30
close). Use the **codes** input to run against a short list while testing, e.g.
`2317,2330,2454`.

### Where the data comes from

`fetch_twse.py` pulls four things from the Taiwan Stock Exchange's open data service:
daily closing prices, company basic data, director and supervisor shareholdings, and
director remuneration.

TWSE renumbers its datasets from time to time, so the fetcher resolves them at runtime
from the service's own API index — preferred IDs first, then a keyword match on the
Chinese dataset title. That's what **selftest** reports on, and it's the first thing to
check if the tables come back empty.

Output is deliberately split in two, because the whole market is ~1,000 boards:

| File | Contents | Changes |
|---|---|---|
| `twse.json` | Light index of every company: code, names, price, market cap, director count | Every run — prices move |
| `twse/<code>.json` | One board: each director's holdings and pay | Rarely — holdings are monthly, pay annual |

The page loads the index once (~200 KB for the full market) and fetches a board only
when you open it. Keeping price out of the shards is what stops a daily refresh from
rewriting a thousand files and bloating the repo.

Two things to know when reading the output:

- **Remuneration is usually a band, not a figure.** MOPS discloses most individual
  director pay in brackets (級距). Those rows are marked `~` in the table and use the
  band midpoint; the top band is open-ended and is floored at its lower bound, so the
  genuinely large earners are understated.
- **Dates come in the ROC calendar.** Filings write 2020 as 109. The fetcher normalises
  both calendars, treating anything before 1911 as an ROC year.
- **Shareholdings are the director's own registered holding.** Shares held through
  family members, investment vehicles or nominees are disclosed separately and are not
  captured here, so a controlling family's true position is often larger than it looks.

Both limitations bias the estimate *down*, which is the right direction for a screen.

Until the first successful run commits a real `twse.json`, the page shows clearly-labelled
synthetic sample data so the layout is still usable — an amber banner says so, and every
name in it is invented.

### Running it locally

```bash
pip install requests
python fetch_twse.py --selftest            # what resolved, writes nothing
python fetch_twse.py --limit 50            # first 50 companies, quick
python fetch_twse.py --codes 2317,2330     # named companies only
python fetch_twse.py --fixture             # synthetic market, no network
python -m http.server 8000                 # then open localhost:8000/prospects.html
```

Serve over HTTP rather than opening the file directly — `fetch()` can't read
`twse.json` from a `file://` URL, and the page will silently fall back to sample data.

## The Source of Wealth estimator (`wealth.html`)

Open `<your-pages-url>/wealth.html`. It is a single static page — no data feed, no
workflow, nothing to deploy beyond the file itself. Two examples ship with it, so you
can see a completed case before entering your own:

- **Listed example** — the case this tool is built for: a chairman and a co-founder of
  an illustrative listed manufacturer, accounts audited from the 2011 IPO onward, both
  stakes marked to market. Loads by default. The company and the people are invented.
- **Memo example** — the desk's original reference case (the family manufacturer with a
  2019 transfer between spouses), anonymised, for checking the methodology against the
  written memo.

**Scope:** directors and controlling shareholders of *listed* companies, where an
audited annual report gives you a defensible net profit and equity figure to work from.

### The methodology

The estimator implements the desk's accumulated-income approach as an ordered
waterfall. Every step is visible on screen, in the step table, and in the draft memo
language, so any number in the file can be traced back to an input:

| Step | What it does | Default |
|---|---|---|
| Distributable profit | Net profit less what the business retains | 40% retained |
| Gross accumulation | Distributable × credited years × ownership %, per ownership period | — |
| Inflation haircut | Erosion of the real value of historic earnings | 20% |
| Prudence discount | Applied **only to periods without audited statements** | 60% |
| Current holding | Their share of book equity — or market cap for a disclosed listed stake | book equity |
| Tax & personal expenses | Final haircut on everything accumulated | 20% |
| Other observed assets | Added after the discounts, not subject to them | — |

**Year recognition** is the judgement call that moves the answer most. The default
credits 48% of each ownership span — roughly the memo convention of discounting 24 of
46 years. Spans are counted inclusively (1972–2018 is 47 years), and the auto figure
is a suggestion: type over the credited-years box on any period to fix it manually.

**Ownership periods** handle transfers. A founder holding 50% until 2018 and a spouse
holding 100% from 2019 are two cards, the second with two periods.

**The prudence discount is per period, not per person** — tick **Aud** on each period
covered by audited statements. This matters for the listed names this tool is for: a
director who took the company public in 2011 has audited accounts from 2011 onward and
unaudited ones before it, and only the pre-IPO years should carry the 60% haircut.
Discounting the audited years too understates the prospect badly, which is the most
common way this methodology goes wrong on a listed name.

**The sensitivity band** under the headline is not a multiplier on the answer — it is
the whole model re-run with the recognition ratio and prudence discount flexed, so the
conservative and upper cases are as defensible as the base case.

**Cross-check lenses** value the same person three other ways — book equity share,
market value of their stake, and cumulative dividends received. They are independent of
the accumulated-income path. When they diverge sharply from the primary estimate, that
is the thing to resolve before the meeting, not after.

### Working a case

1. Enter the company's reporting currency and **overwrite the FX rate with your desk
   rate** — the built-in rates are indicative starting points only.
2. Set "figures entered in" to match how you're typing numbers (units / thousands /
   millions), then enter net profit and total equity straight off the annual report.
3. Use a through-cycle average net profit, not a peak year. The profit history table
   computes one for you.
4. Add a principal per individual, with an ownership period per holding change, and
   tick **Aud** on the periods covered by audited statements.
5. For a current listed stake, set "value their current holding at" to **market cap** —
   book equity understates a disclosed holding in a listed name, often heavily.
6. Read the waterfall, then **Copy text** to lift the draft memo language into the
   source-of-wealth section of the call report.

### Saving and sharing

Cases save to your browser's local storage (**Save** / **Saved ▾**) and export as JSON
for handover. **Print / PDF** produces a clean one-piece memo with the input panel
stripped out.

Nothing is uploaded anywhere. There is no server, no analytics, and no network call
beyond the web font — prospect names and figures stay in your browser.

### Limits worth stating in the file

The output is an *indicative pre-meeting size*, built from public filings plus stated
assumptions. It is not a substitute for documented source-of-wealth verification under
KYC/AML policy, and it does not attempt to capture inherited wealth, non-operating
assets, borrowings against the stake, or holdings outside the subject company. Check
every figure against the filing before it leaves your hands.

## Editing the client list

Edit the `CLIENTS` list at the top of `fetch_news.py`. Each entry can have:

| Field | Required | Notes |
|---|---|---|
| `name` | yes | Display name shown on the card |
| `short` | yes | Short key used internally |
| `type` | yes | One of: `listed`, `sovereign`, `pension`, `insurance`, `bank` |
| `country` | yes | Display label |
| `ticker` | listed only | Yahoo Finance ticker (e.g. `1299.HK`, `7182.T`, `055550.KS`) |
| `aum` | private only | AUM in USD billions, for display |
| `earnings` | optional | ISO date `YYYY-MM-DD` of next confirmed earnings |
| `blurb` | optional | One-line description shown in the detail drawer |
| `newsroom` | optional | URL to the client's press page |
| `sources` | yes | List of news sources, tried in priority order |

Each source has `type` (badge category), `label` (what shows on the card), `kind` (`google-news` or `rss`), and either `query` (for google-news) or `url` (for rss).

After editing, commit the change. The next scheduled run will pick it up, or trigger it manually from the Actions tab.

## Schedule

The default cron `*/30 0-10 * * 1-5` runs every 30 min from 00:00–10:00 UTC, Monday–Friday (Singapore: 08:00–18:00 SGT). Edit `.github/workflows/refresh.yml` to change it.

GitHub Actions sometimes delays scheduled jobs by a few minutes when their runners are busy — that's normal, not a bug.

## Troubleshooting

**"Could not load data.json" error on the page**
→ The workflow hasn't run yet, or it failed. Check the Actions tab.

**Workflow fails with permission error**
→ You skipped Step 4 above. Go back and grant write permissions.

**Cards show "no source"**
→ The fetcher couldn't reach Google News for that client. Could be transient — try re-running. If persistent, the `site:` filter for that domain may need to be broadened.

**Yahoo quote endpoint stops working**
→ Yahoo occasionally changes endpoints. If quotes go missing, the chart endpoint in `fetch_quote_chart()` is the most-stable replacement; for production-grade reliability, swap to a paid feed (Polygon, IEX Cloud, FMP).

## Not for client distribution

Both tools are for internal use. The dashboard aggregates publicly-available news and
price data; not investment advice. The wealth estimator produces indicative internal
sizing from public filings; it is not a valuation, not advice, and not a client-facing
document.
